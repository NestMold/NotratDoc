# 1.3.7

发布日期：2026-11-02　·　[← 上一版](/changelog/v1.3.6)　·　[下一版（开发中） →](/changelog/v1.3.8)

## ⚡ 更新亮点

- **🧭 顶部多了一排「文件 / 编辑 / 视图」菜单栏**：点文件树头上那枚 ▾（工作区菜单），除了原来的工作区下拉，文件标签正上方还会滑出一条菜单栏——文件(F) / 编辑(E) / 视图(V) / 导航(N) / 设置(S) / 帮助(H)，每一项右边都标着它对应的快捷键。不熟快捷键的人可以直接点：保存、打开文件、关闭标签、切换深色、文件树 / 大纲 / 反链 / 搜索 / 终端、全局搜索，以及直接落到设置里某一页。菜单开着时鼠标划到别的分类会直接换菜单（不用先关再点）；Esc 先收下拉、再按一下收整条栏；点栏外任何地方收起。菜单栏长出来时只把文件标签和它下面的内容往下压——左边文件树、右上那组控件（编辑|源码 / 控制带 / 窗口按钮）原地不动。
- **🔗 AI 会查「谁引用了这篇笔记」，也会看局部图谱**：笔记库里新增两条工具。`knowledge_backlinks` 查一篇笔记的反向链接（哪些笔记用 `[[链接]]` 指到它），同时给出它自己链出去的是哪些；`knowledge_graph` 看 N 跳内的局部图谱（默认 1 跳、最多 3 跳，可选只看被引用 / 只看引用出去）。两条**不需要先建索引、也不需要打开「启用知识库」**，直接读盘算，免费档也能用——「这篇笔记和哪些内容相关」这类问题，AI 终于不用靠猜。
- **🧠 知识库常驻内存少了约 135 MB**：本地向量模型以前实际加载的是 fp32 权重（94.8 MB），代码里却写着「int8 约 24 MB」——因为本地推理库在后续版本里改了这个参数的名字，老参数被静默忽略。现在按真实权重文件判断并加载 q8（24.5 MB）：实测模型加载后进程内存 +83 MB，而 fp32 是 +218 MB。老用户的缓存里只有 fp32 时不会偷偷替你下 25 MB，继续用原来那份。
- **🧠 反链 / 图谱扫描改成一条一条过，不再把整个工作区读进内存**：以前一次反链查询要把工作区里每篇 markdown 的解析结果全留在内存里；现在 8 路并发读、算完一篇丢一篇，只留命中的结果。单文件也先看大小再读——超过上限的 md 直接跳过，不再出现「先读进堆再判断超限」的白占峰值。实测 4.4 万条分块的向量缓存也在关闭知识库时一并释放。
- **🔄 插件更新在全应用只剩一套**：插件箱、自动检测、市场面板、扩展管理 → 插件，四处以前各算各的版本、各走各的更新。现在版本比较、可更新判断、更新应用、装完对账都收敛到同一处：市场卡片点「更新」不再每次都问一遍装到哪个范围（选成全局就在工作区里多装一份副本），装完更新记录也会清掉，角标跟着消失；「本机是 1.9.2、货架是 1.0.1」这种降级情况也不会再亮「可更新」。打开插件箱抽屉、市场面板或扩展管理页时都会顺手补检一次（同一份检查、1 小时节流），长时间不重启也不会各处显示不一致。
- **🖱️ 插件的右键菜单补齐了**：活动栏上的单个插件按钮右键，以前只有「上移 / 下移 / 隐藏」，现在还能打开面板、检测更新、更新到 vX、重载插件、插件设置、在扩展管理中查看——检测 / 更新 / 重载进行中时文案就地变成「检测中… / 更新中… / 重载中…」，做完再关菜单。插件箱入口按钮右键也补了「检测插件更新」（行尾顺手写「N 个可更新」）、「更新全部插件 (N)」和「打开插件管理」；插件箱里的插件卡片右键新增「检测更新」，查到最新会给一张「✓ 已是最新」的回执，不再是点完什么都不发生。
- **💬 压缩不再吞掉最后一条**：触发压缩后，最后一条刚收到的回复以前会从屏幕和存档里一起消失。原因不只是「写错了」，而是压缩拿的是本窗口手里的那份会话快照，别的面跑完的回复、后台流的结果可能只落到盘上——现在压缩先读盘上最新那份，再把「屏幕上已经在、快照里没有」的消息按原位置接回去，压缩只允许把旧历史折进摘要，不许删任何一条看得见的消息。
- **🧠 长对话不再「聊到一半忘了我在干什么」**：摘要以前只记「进行了 N 轮工具调用（name1、name2…）」——等于用一张只记了动作名的废纸换掉整段历史，模型只能从尾部几轮重新猜意图。现在摘要必须写进**用户的原始要求和助手的结论**；同时摘要本身在上下文里改成 system 身份，不会被「从新往旧保留」的截断规则每轮第一个砍掉——实测 47 条消息、35 万 token 的一盘对话，模型对「这盘在干什么」的唯一记忆以前恰好最先出局。
- **🔗 压缩不再让回复「到一半没下文」**：压缩是「分段摘要 + 合并」的长流程，以前会和截断续写、排队消息、子 agent 抢同一个服务商——大请求一跑几分钟，续写就躺在队列里干等。现在压缩只在**真正空闲**时开闸（子 agent 在跑、续写链没收尾、队列里还有本会话要发的消息，三条任一命中就等），并且压缩请求本身有硬上限：单条消息进摘要前截到 4 万字符（长命令输出是真正的体积来源），单次请求按保守口径估算后不超过 12 万 token——现场出现过 2.48 MB / 1.53 MB 的单片请求被服务端直接以「prompt is too long」拒绝。
- **🗂️ 子 agent 卡片跟着会话走**：在主页开一条新对话时，上一条对话的子 agent 卡片（任务流 / 子 Agent 页签）以前会整排留在面板上；现在卡片在第一次出现时盖上所属会话的章，只显示当前会话的，切回旧对话时原样回来。判断「还有没有子 agent 在跑」改成读全量盖章表——别的会话在跑的任务照样会拦住切工作区 / 刷新。
- **🪟 从主页对话跳进工作区，AI 侧栏不会再消失**：聊到一半点一条对话跳去工作区，以前侧栏会被「借来的开合状态」还原成关闭，跳过去只剩文件和编辑器。现在跳转前先清掉接管存档、把面板列打开，跳过去就是为了让你看见这条对话。
- **🎛️ AI 弹出来的选项面板，键盘就能答**：选项卡片（单选 / 多选 / 分步向导）生成完的那一刻，键盘焦点会自己落到这张卡上——你正在别处打字就不接，历史会话里翻出来的旧卡片也不会挨个抢（只认「刚刚生成完的那一张」）。↑↓ 在选项间走（单选走到哪选中哪，多选空格勾选），←→ 翻页（分步向导的下一步 / 上一步，最后一步就是提交），回车确认或翻页；点卡片空白处也能把方向盘接回来。卡片不是弹窗：不拦 Esc、不做焦点锁定，点别处焦点照常走。**回复一结束也是它先拿键盘**：只要这条回复带着面板、输入框里又没有草稿，焦点直接落在面板上，不用先按 ↓ 或拿鼠标点一下；想回输入框按 Esc，或者干脆开始打字——第一个字会一起带进输入框；输入框空着时按 ↓ 也能随时把焦点交给面板。
- **⌨️ 文件树：点了一个文件之后，方向键也能接着走**：以前点文件只是「选中」，焦点没交给树，方向键（↑↓ 选、←→ 收起 / 展开 / 回父级）整组像死的。现在点行就把键盘交给树。在树里直接打字**只跳行、不过滤**——别的文件不会被筛没，也不再弹提示条；要过滤就在搜索框里打字、**按回车才生效**，框里的字还在、树先不动，删空即撤。搜索框 Esc 清词、词空了再按一下退回树，↓ 直接进列表接着按方向键；搜索定位也不再把你从搜索框里踢出去。
- **🤝 外部 agent（A2A）派进来的任务，现在真的会动手**：A2A 端口以前接的执行器只会说话——外部 agent 派一句「跑一下测试并把报错修掉」，拿回来的只有一段描述。现在换成和定时任务同一套、带工具的执行引擎：连接器（MCP）、终端、文件、技能都能用，任务在主进程跑、不占窗口。取消之后迟到的结果也不会把「已取消」改写成「已完成」；没设 token 启动时会在日志里明确告警——带工具之后，这个端口等于「本机任意进程可以让你跑命令」。
- **⚙️ 设置里能自己关掉硬件加速**：设置 → 通用 多了一行「硬件加速」开关，默认开着。关掉之后下次启动改用软件渲染（界面交给 CPU 画），显卡驱动爱闹别扭的机器可以就这么长期用着；拨动即保存，旁边会提示「重启 Notrat 后生效」，不用再点「确定」。处在自动降级状态时，这个开关显示的是真实的「关」，不会骗你说还开着。
- **🛡️ 显卡进程连续出事，应用会自己退一步**：同一个 7 天里显卡进程崩了两次，下次启动自动切成软件渲染，并在角落弹一条提示：「检测到显卡驱动异常，已关闭硬件加速（设置里可重开）」。只弹一次，不反复打扰；不自动重启应用，也不偷偷每隔一会儿再试一次硬件加速——界面照常可用，你自己在设置里重新打开就解除。
- **🩺 崩溃记录带上了现场**：以前后台只留一句「显卡进程异常退出」；现在同一条记录旁边会写上显卡型号与驱动版本、崩溃那一刻开着几扇窗口、进程数与内存 / 显存占用。下一次遇到同类问题，不用再从你的描述里拼现场。
- **🖐️ 当前正在看的那条也能拖走了**：以前把正在看的对话拖到另一个工作区，会提示「无法移动对话——先切到那个工作区的另一条对话」，得先手动点开另一条再回头拖。现在直接拖就行：会先替你切到源工作区的另一条对话（没有就开一条空的），再整条搬过去。另一个窗口正开着这条时，它会被提示「这条对话已被移到其他工作区，已为你切到别的对话」并自动让开，不会两个窗口守着同一条抢着写。
- **🧩 子 Agent 做完的结果，就在那一轮的 agent 卡里**：后台子 Agent 交回来的结果不再伪装成一条「你发的消息」插进对话流，而是并进本轮 agent 卡（和工具调用同一张卡）的展开区，每条一块结果卡：标着「结果 / 失败」、Agent 名、耗时，下面是它交回来的正文。跑完的活终于看得见，过程仍旧只留在底部运行面板里。

- **🏷️ AI 服务商能改名，同一个服务商也能配多条**：设置 → AI 配置里，每条服务商都能在表单最上面改「名称」——以前只有「自定义系」才有这个输入框，预设品牌想区分也没处改。同一个品牌再点一次「添加服务商」，以前会直接把旧那条覆盖（第二个 Key 存进去、第一个就没了），现在自动另起一条（「GLM 2」），各用各的 Key、地址和模型列表；不改名也会自动带上序号，列表里不会出现两条一模一样的。

### 🚑 发消息卡 5~8 秒：会话广播的递归风暴

- **来由**：2026-10-30 用户「发消息跳转过去卡顿，跳过去继续回复」。同一台机器的日志里，这条 5~7 秒的卡顿一天出现 10 次。
- **症状**：点「新对话」或「发送」之后整窗卡住 5~8 秒，鼠标点不动；恢复后用户消息才落盘、请求才发出去。日志里 `Maximum call stack size exceeded` 成片刷。
- **以前**：保存会话时结尾会**同步**广播「会话列表变了」，而订阅者（会话列表）在回调里**同步**读列表、读的时候又顺手把标题改好再保存一次——save → notify → save → notify 一层层叠到爆栈，每层还各带一次同步 IPC（实测一秒近两百次），主线程被占死。放大器是标题自愈：它一律把改好的标题写回**调用方那个桶**（主页的聚合列表 = 全局桶），会话真正所属的工作区桶里标题永远停在「新对话」，于是下一次渲染又判定要自愈、又存盘又广播。
- **现在**：广播加重入闸门——重入只记一笔「待补」，最外层这一轮跑完再补发（最多补 3 轮，防止订阅者互相踢皮球），递归深度不再随订阅者行为增长；标题自愈按会话**自己所属的工作区**分组写回各自的桶，目标桶里没有这条会话就不写（不凭空造一份跨桶副本、下次启动多一条重复）；同一条会话的同一次改名只试一次，写盘失败也不每帧重试。
- **边界**：列表里「新对话」→ 真标题的自愈仍需一次落盘（罕见路径，只在真有未命名会话时发生）；主页聚合列表仍不把完整会话树留在内存里。

### 🎞️ 回复到一半整窗卡死：流式渲染改成每帧最多一次

- **来由**：2026-10-30 用户「卡死之后，回复完了才跳过去」——那台机器比开发机还强，所以不是算力问题。
- **症状**：回复流式输出期间整窗没有响应，连侧栏都点不了；回复一结束，画面一次性跳到最终内容。
- **以前**：流式内容、工具调用、思考过程三个旁路通道每收到一个分片就**同步**通知一次订阅者，等于每个分片排队一次 React 渲染（每次都要重新解析整段正在增长的 Markdown）；网络快于重绘的机器上队列只增不减，主线程被一路饿到回复结束。跟随滚动同样在每一片上都取消并重启一次「12 帧 settle」循环，每帧强读滚动高度。
- **现在**：三个通道的写入只改值，通知合并到**每帧最多一次**（rAF；没有 rAF 的环境 16ms 兜底），只保留最新值；流结束立刻广播一次，最后一帧内容不会晚一拍。跟随滚动也合并到每帧最多一次，卸载时取消挂起的回调。另加三只探针写日志：渲染层超过 1 秒的长任务（带「发送 / 流式 / 收尾」阶段标签）、主进程事件循环漂移超过 1 秒、rAF 明显迟到——用来区分「窗口堵」还是「主进程堵」，不必再靠猜。
- **边界**：这是限流不是降级——读值永远是最新的；任何新代码不许假设「写完订阅者就已经收到」，要立刻可见就显式 flush 一次。

### 🔌 发出去没反应：SSE 端口只发给了主窗口

- **来由**：2026-10-30 实测日志：打包版和开发版同时开着时，每一次发送都连不上本地服务（`Failed to connect to SSE server after 3 attempts`），用户看到的就是「发消息没反应」。
- **症状**：打包版发消息毫无反应，日志里反复连不上本地 SSE 服务；把开发版关掉就恢复。
- **以前**：服务启动时 46813 已被开发版占着，打包版退到 46814 起——而「真实端口」只在开服那一刻广播一次，那一刻通常一扇窗口都还没有（模块求值期就开服）；广播又只发主窗口，浮窗、插件窗、多开的第二扇窗一律漏掉。于是渲染层永远停在默认端口 46813，请求要么打进开发版那边，要么打向死端口。
- **现在**：端口广播发给**所有窗口**；每扇窗每次（重新）加载后按当前端口再补发一次；日志写明「通知了几扇窗 / 暂无窗口，等加载完补发」。
- **边界**：端口仍从 46813 起挑可用端口；多个实例同时开时各用各的端口，不再互相串。

### 🛡️ 显卡进程崩了两次，下次启动自动改用软件渲染

- **来由**：2026-10-31 有用户遇到显卡进程异常退出之后整机死机、托盘消失，只能手动重启。这类问题是显卡驱动把图形上下文丢了，应用修不了，但可以少让用户再撞一次。
- **以前**：崩了就是崩了，下次启动照样用硬件加速，同一台机器上会反复发生；也没有任何地方记录「这台机器最近崩过几次」。
- **现在**：应用在本地记一本显卡崩溃流水（7 天窗口）。窗口内累计到 2 次，就进入安全模式：把「关闭硬件加速」写进设置，下次启动直接以软件渲染运行，并在界面弹一次说明。单次偶发不降级；已经在安全模式里再崩，只继续记流水，不会每崩一次弹一次。
- **边界**：不自动重启应用、不自动再试硬件加速——解除只需要在设置里把「硬件加速」重新打开；应用自己退出、重载带走的显卡进程不算崩溃，不计入流水；安全模式期间，别处保存的整份设置不会把开关翻回「开」，只有设置页那个开关能解除。

### 🩺 崩溃记录：补上显卡型号、驱动版本和当时的进程占用

- **来由**：10-31 那次只拿到「显卡进程异常退出」这一句，显卡型号、驱动版本、当时开了几扇窗、内存涨到多少，全靠事后问用户。
- **以前**：崩溃上报只有类型、原因和退出码；显卡相关的问题尤其缺上下文，同一个现象背后的机型差异完全看不出来。
- **现在**：显卡进程退出、窗口进程退出、页面加载失败这三类记录，都会顺带写上显卡型号与驱动版本、窗口数、进程数与内存 / 显存占用。字段都是短的文本，不改变原有的上报数量和内容口径。
- **边界**：显卡信息在启动时异步取一次（取不到就留空，不拖慢启动）；内存数字以系统给出的工作集为准，跟任务管理器里的读数可能有小幅出入。

### ⌨️ 选项面板：回复一结束就接过键盘，Esc 或直接打字退回输入框

- **来由**：2026-10-30 用户「AI 回复的选项面板弹出来之后，在应用内做一次聚焦，但不影响其他使用；上下方向盘选择，左右方向盘翻页，回车也是翻页或者提交」；2026-10-31 又提「AI 回复完了之后，如果有面板的话，光标还是在输入框上面，而不是在面板上面，除非用户一直按 ↓；减少鼠标化，用户能用键盘完成的事情，就不用鼠标完成」。
- **以前**：选项卡片（单选 / 多选 / 分步向导）只能用鼠标点；键盘得 Tab 一路走过去，方向键在卡片里什么也不做。后来卡片挂载时会接一次焦点，但回复结束时焦点几乎总在输入框里，而焦点在文字输入处时不抢——于是面板在最该用键盘的那一刻永远拿不到键盘，只能拿鼠标点一下；焦点进了面板后，想回输入框也只能再点回来。
- **现在**：卡片定稿挂载后接一次键盘焦点（卡片是 `tabIndex={-1}` 的普通节点）；只有选项 / 向导两种卡片接，任务流和快捷按钮不接。回复一结束，只要这条回复里带着交互面板、而输入框里没有草稿，焦点就直接落在面板上——↑↓ 选、←→ 翻页、回车确认马上能用。想回输入框按 Esc，或者直接开始打字：第一个字会一起带进输入框，不会白按。输入框空着时按 ↓，也能随时把焦点交给最后一张面板。
  - 键位：`choice-form` ↑↓ 移动高亮（单选走到哪选到哪，多选空格勾选），回车确认（还没选时先把高亮那行选中，第二下才提交）；`ask-wizard` ↑↓ 移动、→ / 回车下一步（最后一步 ＝ 提交）、← 上一步、空格勾选多选。
  - 高亮行保持在可视范围内；卡片拿到焦点时描一圈焦点环，鼠标点卡片空白处也能把方向盘接回来。
  - 单选 / 多选的原生控件例外——点行之后浏览器会把焦点给那枚 radio / checkbox，方向键由卡片统一接管（原生 radio 只认同名分组，跨卡片会串台）。
- **边界**：不是模态，不设焦点锁定，点别处焦点照常走；输入框里已有草稿不抢，正在别处打字不抢（@ 面板搜索框、文件树搜索框、行内重命名），窗口不在前台不抢。只有「刚生成完的那一张」会自动接焦点——流式预览时给这张卡盖一个戳，定稿挂载时凭戳消费一次，打开历史会话时几十张旧面板不会挨个抢。焦点用「不滚动」的方式拿，滚动自己算：卡片完全在视口里就不动，否则只滚到最近可见。向导换步时高亮回到「这一步已选中的那项」，没有就回到第一项；步骤里的自由输入框自己处理按键，不被卡片截走。

### ⌨️ 文件树：方向键、只定位、回车才过滤

- **来由**：2026-10-30 用户四轮原话：「FileTree 文件选择也要支持方向盘」「直接输入会过滤掉其他选项，这里不要过滤，只有用户按下搜索才过滤」「用户没有按回车定位，按了回车才过滤」「FileTree 定位的话，编辑框失焦了」。
- **以前**：点一个文件只是「选中」，键盘焦点没交给树——方向键像死的；在树里直接打字会把字灌进搜索框、整棵树被筛掉；搜索框边打边筛；搜索定位会把焦点从搜索框抢到树上；窗口一窄，搜索框死守 50px，把工具条右端的按钮挤出边缘。
- **现在**：
  - 点行时把焦点交给树（`role="tree"` 那层），↑↓ 选、←→ 收起 / 展开 / 回父级由文件树组件自己接管；行内重命名 / 新建的输入框照旧自己留焦点。
  - 树里直接打字＝**只定位**：走组件自带的前缀跳行，不写搜索框、不过滤，树始终是完整那棵，也不弹任何回显提示。
  - 过滤只由搜索框触发，且**按回车才生效**：框里的字实时显示，树等回车再筛；删空输入框立刻撤掉过滤。
  - 搜完之后把光标落到**第一个真命中的文件**（筛出来的第 0 行可能只是名字不含关键词的父目录），只选中、只滚动，不碰焦点；焦点原来在搜索框里就原样还回去。
  - 键盘接力：搜索框 ↓ 进树、Esc 清词（词已空再按一下退回树）；树里 Esc 有词时先清搜索；树里回车仍是打开文件 / 文件夹。
  - 窄窗：展开态可以缩到 0（`min-w-0`），收起态的实宽在余量不够时也继续让步到 0——宁可搜索框窄到看不见，也不把工具条按钮顶出右缘。
- **边界**：树里打字只认字母数字前缀；想按内容搜仍走搜索框那一路（那里有「文件 / 内容」切换）。窄窗让位只影响搜索框宽，不改变「哪几枚按钮收进 ⋯」的判据。

### ⚙️ 硬件加速：出问题的时候，自己能关掉

- **来由**：2026-10-31 有用户遇到显卡驱动问题之后整机死机，而此前应用里连一个开关都没有。
- **以前**：硬件加速一直开着，没有设置项；驱动不配合的机器只能每次等它崩，也没有任何办法长期改走软件渲染。
- **现在**：设置 → 通用 新增「硬件加速」开关，默认开着。拨动即保存，旁边写明「重启 Notrat 后生效」。关闭后下次启动界面改由 CPU 绘制，显示效果与操作方式不变，只是重负载的画面（大图谱、大量动画）会慢一点点。
- **边界**：开关只在启动时生效，改完必须重启才能体会到；处在自动降级状态时，开关显示的是真实状态（关），不会被别处保存的旧设置覆盖；只有明确关掉才算关，配置文件里写成字符串之类的手改脏值一律按「开」处理。

### 🖐️ 拖走当前对话：不用先切走，别的窗口也会跟着让开

- **来由**：2026-10-31 用户拖对话时被提示「无法移动对话 —— 这条对话是它所在工作区的当前对话。先切到那个工作区的另一条对话，再拖过来。」

### 💬 压缩：最后一条不再被吞掉

- **来由**：2026-10-30 用户「触发压缩后最后一条内容丢失」。

- **现在**：压缩读会话时先取**盘上最新那份**（本进程模块缓存 = 所有实例最后一次写入），`currentSession` 只在读不到或还是桩时兜底。压缩完成后的显示列表 = 压缩后的会话快照 ∪ 屏幕上已经在的消息——「本地有、快照没有」的按原顺序接回它前一条后面，锚点找不到就接在最前。摘要卡不进分支（它只属于显示层，由压缩位置拼回），也不写进消息路径。
- **边界**：压缩只允许把旧历史折进摘要，不许删任何一条看得见的消息。清缓存跟着压缩实际读的那份会话 id 走。

### 🧠 压缩：摘要要记住你要过什么，且不能每轮第一个被砍

- **来由**：2026-10-29 用户「对话压缩会导致对话断流」；同日又报「中间意图识别都错了」。
- **症状**：长对话压缩过几轮之后，AI 开始答非所问、反复从尾部几轮重新猜用户的意图，好像完全忘了前面要求过什么。工具调用一多尤其明显。
- **以前**：两处叠加。① 摘要模板只写「进行了 N 轮工具调用（name1、name2…）」——工具名对判断意图毫无价值，用户的句子才是；等于拿一张只记了动作名的废纸换掉整段历史。② 摘要卡一直是 `role=assistant` 且永远排在第 0 位，而发送侧截断只无条件保留 system 消息、其余从新往旧保留——于是摘要**每轮第一个出局**。实测一盘 47 条消息 / 35 万 token 的对话，模型对「这盘在干什么」的唯一记忆恰好最先被砍掉。
- **现在**：
  - 摘要必须写进**用户消息原文**（每条保留 300 字符、助手结论 200 字符、最多 6 条结论、正文预算 4000 字符）——需求原文是唯一不能丢的东西，但摘要自己也不能膨胀成第二个大 payload。
  - 摘要卡在**上下文口径**里换成 system 角色，跟系统提示词一起被保住（三家 provider 都接受多条 system）；显示层照旧按 assistant 认这张卡，界面上没有任何变化。落盘的节点不会写成 system。
  - 发送前清洗多了一条：丢掉「[响应被中断]」这类只给眼睛看的占位（无工具调用的空壳）。带 toolCalls 的中断消息必须留着，它要跟紧跟其后的工具结果配对。顺带修好了「同一句话重发两遍」被占位卡住相邻去重、模型把意图从头再猜一遍的问题。
- **边界**：只改上下文口径，不改存档；历史会话打开后自动享受同一套规则。

### 🔗 压缩：不再抢流断流，排队也不再堵死

- **来由**：2026-10-29 用户「对话压缩会导致对话断流」，同日报「压缩的时候消息排队也有问题」。
- **症状**：回复到一半突然停了，几分钟没有下文；压缩期间在横幅上点「发送」没有任何反应；一条会话的排队消息一直挂在队首时，另一条会话排的消息永远发不出去；偶尔压缩请求直接失败（服务端返回「prompt is too long」）。
- **以前**：① 压缩原本在「截断续写之前」先跑——但续写断的是**输出上限**而不是上下文窗口，压缩换不来续写需要的空间；而压缩是「分段摘要 + 合并」的长流程，现场一个 2.4 MB 的请求跑了 3.5 分钟，后面还有两片 476 KB 各跑 40 秒，续写一直躺在延迟队列里。② 压缩请求的体积失控：长命令输出一条就几十万字符，而分片逻辑没法把一条消息拆开，于是单条消息自己就成了远超窗口的分片；token 估算统一按 3 字符/token，对「中文 + 全角标点 + 代码混排」低估 2–3 倍——1,528,117 字符的请求服务端算成 1,705,981 token，我们估成 509k，判断「没超窗口」就发了出去。③ 出队只看队首，且压缩在途时按钮不做处理。④ 压缩完成后套用的是「压缩开始时的快照」，会把期间刚发出去的消息抹掉。
- **现在**：
  - 压缩只在**真正空闲**时开闸：子 agent 在跑、截断续写链还没收尾、队列里还有「会发在本会话」的消息——三条任一命中就等。别的会话的手动排队消息不算（它会一直挂着等用户切回去，不能永久禁掉本会话的自动压缩）。
  - 单条消息进摘要前截到 4 万字符（头 60% / 尾 40%，中间标注省略量）；单次压缩请求的 token 预算上限 12 万；token 估算改成保守口径——ASCII 按 4 字符/token，其余（中文、全角标点、制表符、emoji）一律 1 字符/token。宁可分得碎一点，也不能因为估小被拒。
  - 压缩期间用户手动点「发送」= 明确要立刻发：放下在途标记、让这次（按压缩开始时快照算的）结果**作废**，消息当场发出去。
  - 出队按消息下标摘，不再假定队首；并且只看「会发在本会话」的条目。
- **边界**：压缩仍是后台优化，不会和正在跑的东西抢同一个服务商。压缩期间手动发的消息会带着当时的快照走（见下一节）。

### 🗂️ 子 agent 卡片：归属哪条会话，一出生就定

### 🧩 子 Agent 的结果：并进那一轮 agent 卡

### 🧠 知识库内存：模型按 q8 加载，扫描改成一条一条过

- **来由**：用户要求把内存占用压到运行时允许的极限，随后追问「3（本地向量模型）会占用多少」。
- **症状**：本地嵌入模型加载后进程内存涨得比预期多一倍不止；反链 / 图谱在笔记多的工作区上一跑，内存就顶上去一段时间。
- **以前**：两处。① 代码里写的是 `quantized: true`，但本地推理库在后续版本里改了这个参数的名字（`quantized` → `dtype`），旧参数被**静默忽略**——所以一直加载 fp32 的 `model.onnx`（94.8 MB），注释里那句「int8 约 24 MB」从来没成立过。② 反链 / 图谱的扫描先把整个工作区每篇 markdown 的解析结果全攒在内存里再算；「文件太大就跳过」的判断写在 `readFile` 之后，等于先把几十 MB 读进堆再判断超限。
- **现在**：
  - 按真实权重文件选档：有 `model_quantized.onnx` 就请求 q8，只有老的 fp32 就继续用 fp32（不替你偷下 25 MB），一份都没有时也请求 q8。实测（独立 node 进程，bge-small-zh-v1.5）：fp32 加载 54→272 MB（+218，卸载后仍占 182）；q8 加载 54→138 MB（+83，卸载后 114）——**省约 135 MB**，比「闲置一会儿就把模型卸掉」划算得多（卸载只能收回 90 / 24 MB，其余是运行时和 arena 留在进程里）。
  - 「已下载」的判断改成看真实权重文件，不再只看缓存目录名——否则 `downloadMode: "ask"` 的设置会被绕过、静默联网补下。
  - 反链 / 图谱改成 8 路并发流式扫描，算完一篇丢一篇，只留命中的结果；单文件先 `stat` 看大小再读，超限直接跳过。
  - 关闭知识库时，把向量缓存和分块 id 表一起释放（4.4 万条分块 × 1024 维 ≈ 180 MB）。
- **边界**：缺省开关仍按整机内存定（> 24 GB 默认开、≤ 24 GB 默认关），这一版没有改；老用户缓存里只有 fp32 时不会自动改档，想验证 q8 通路得删掉 profile 下的 `model.onnx`。闲置卸载没有做——收益只有上面那几个数字，不值得复杂化。

- **症状**：同一屏里两套版本口径（市场卡片按「不相等」算、插件卡片按另一套解析），本机装的是内部迭代号 1.9.2、货架上是 1.0.1 时也亮「可更新」；市场卡片点「更新」会再弹一次安装确认，每次都再选一遍作用域，选成全局就在工作区里装出第二份副本，装完更新记录也不清，插件箱的角标继续挂着；插件箱里早就亮角标，扩展管理 → 插件页却要手点「检测更新」才认。
- **以前**：四处各写一份版本比较和「怎么算更新」，更新动作也各走各的落地路径（市场那条复用了「安装确认弹窗」，等于把「更新」当成一次新安装）。
- **现在**：
  - 版本比较、可更新判断（严格大于才算）、更新应用、装完对账、自动检测的时钟与节流，全部收敛到插件更新服务一处。
  - 市场卡片的「更新」与插件箱 / 扩展管理走同一个动作：按**当初装的位置**重装、成功后摘记录、角标跟着消失；工作区档会回到台账里记着的那个工作区，不再装进「当前窗口」的目录。
  - 更新记录对账在服务层做（装完 / 卸载 / 手动更新后角标必须消失），四个插件表面引用同一份。
  - 打开插件箱抽屉、市场面板、扩展管理 → 插件页时都会顺手补检一次（同一份检查、1 小时节流）；启动后的自动检测仍是「8 秒后首次、最短 6 小时一次」。
- **边界**：自动检测的时钟仍按「所有人都走同一份」，多窗口同时开着时不会各检一遍。台账里没有工作区根的老记录，会从安装路径（`<工作区>/.notrat/plugins/...`）反推出来，不用重装。

### 🖱️ 插件右键菜单：活动栏 / 插件箱入口 / 插件卡片

- **来由**：2026-10-29 用户「ActivityBar 插件选项的右键菜单也可以补全」，随后又补一句「插件箱里面也可以右键检测更新吧」。
- **以前**：活动栏上的插件按钮和普通按钮共用那段手写菜单，只有「上移 / 下移 / 隐藏此按钮」；插件自己的动作全得先点开插件箱抽屉、再右键卡片。插件箱入口按钮的菜单只有「挪位置 / 隐藏入口」。
- **现在**：
  - **活动栏插件按钮**：打开面板、检测更新、更新到 vX（有更新才出现）、重载插件、插件设置…（有设置表单才出现）、在扩展管理中查看，下面是上移 / 下移 / 隐藏此按钮（首项不能上移、末项不能下移，禁用态直接灰掉，不再是点了没反应）。菜单用的全应用通用右键菜单，带图标、整强度描边。
  - **插件箱入口**：检测插件更新（行尾直接写「N 个可更新」）、更新全部插件 (N)（有货才出现）、打开插件管理。
  - **插件卡片**：新增「检测更新」，查到最新给一张「✓ 已是最新」回执；有更新则角标和「更新到 vX」项由记录驱动自动出现。
  - 三条异步通道（检测 / 更新 / 重载）点完不立刻关菜单，就地显示「检测中… / 更新中… / 重载中…」，做完再关——右键菜单一关就没别处能落结果了。
- **边界**：插件按钮已禁用 / 卸载但配置里还留着那一格时，右键退回原来的「上移 / 下移 / 隐藏」，至少能把它挪走。排序仍按**屏幕上**的顺序换邻居（折叠逻辑会把当前项从折叠区换回可见区，按配置顺序换会出现「点了上移纹丝不动」）。

### 🧩 按工作区安装的插件：台账记住是哪个工作区

- **来由**：2026-10-29 用户「插件按照工作区来安装有 bug」。
- **症状**：同一个插件在两个工作区里分别装过，台账里变成两条「工作区档」，但谁也说不清哪条属于哪个目录；换工作区后再点更新，新副本会装进当前目录，原目录那条永远等不到更新。
- **以前**：安装台账是全局一份（`%APPDATA%/<app>/installed-plugins.json`），以前只记 `scope: "workspace"`，不记是哪个工作区。
- **现在**：工作区档的记录必须带工作区根，安装 id 里也带上它的短哈希（绝对路径归一化大小写——同一个目录换个大小写写法，不能算两次安装）。老记录没有这个字段时，从安装路径反推工作区根，不用重装。
- **边界**：台账格式向后兼容；只有真的换了工作区去更新，才会出现两条记录指同一个工作区的情况，这一版由 id 归并掉。

### 🤝 A2A：外部 agent 派进来的任务，现在会真的调工具

- **来由**：2026-10-30 用户「我的意思是之前 A2A 不能调用 MCP 吗」→「先把 A2A 工具给修复吧」。
- **以前**：远程助手的 A2A 端口接的是「纯问答」执行器——只往本地发一条没有工具表的请求。外部 agent 派「跑一下测试并把报错修掉」这类活，拿回来的只有一段描述。 不是能力缺失，是执行器接错了线。主进程本来有两条路：一条纯文本（给「LLM 改写」这类用），一条带工具（定时任务、IM 用，工具在主进程执行、结果直接回填）。A2A 接在了前者。
- **现在**：换成带工具的那条（与定时任务同一个引擎）：连接器（MCP）+ 内置终端 / 文件 / 技能 / 通道，工具在主进程执行、不经过窗口；定时任务那套「没调工具就再催一遍」的评测器关掉（那是给「必须产出结果」的定时任务写的，问答型 agent 会被误判未完成、白烧最多 3 轮）；取消任务之后迟到的结果直接丢弃，不会把「已取消」改写成「已完成」；没设 token 时启动明确告警。
- **边界**：agent 列表仍由窗口同步——开着 A2A 但一次都没打开过 AI 对话时，会回 `no agents configured`。端口只绑本机回环地址；带工具之后建议一定设 token，否则本机任何进程都能通过它让你跑命令。

::: details 🔧 后台小修 · 6 则

1. **重装到别的目录后插件面板整片编译失败**：用户级环境变量 `ESBUILD_BINARY_PATH` 会一直指着老安装目录，老目录没删干净时文件检查也照样通过，于是把旧二进制当成自己的用。现在打包版里这个值只有落在**本次运行的这个安装目录内**才算数；指向别处会打一条带排查提示的日志，然后按包内布局重新钉。另外新增一个显式覆盖变量 `NOTRAT_ESBUILD_BINARY_PATH`（排查 / 支持用，优先于一切，但只认真实存在的文件）。
2. **换目录重装后旧安装目录留在盘上**：旧卸载程序失败时，「继续覆盖安装」这条兜底让新版本装得下，但旧目录原样留着（0.7–1.2 GB），下次换目录再叠一份。现在失败时顺手把旧目录清掉——位置从注册表 `InstallLocation` 读，三条护栏缺一不可：有旧安装位置、不是这次要装的目录、里面确实有我们的安装痕迹；先删保留设备名文件再递归删。perMachine 安装时那一遍按当前用户走的旧版本检测也补了同一个兜底（以前会落到默认的「弹框 + 退出」）。
3. **右键菜单描边太淡**：`border-border/50` 那圈压在浅底标签栏和一般正文上几乎看不见边界，浮层像直接糊在内容上。全站右键菜单统一改成整强度描边，和工作区下拉对齐。
4. **设置深链只生效一次**：已经停在外观、点去通用、再从菜单点「外观」——prop 前后都是同一个值，React 认为没变，「只应用一次」的闸门也不放行，菜单点了没反应。现在设置页收下请求就回报「已消费」，上层把值清回 undefined，下一次同一个分类是货真价实的新值。
5. **文件树列不再被菜单栏压缩**：文件树自成一根独立的列，头部和面板一起吃满高度；把手跟着面板搬到面板左缘，不会再压住第一枚页签。
6. **知识库工具的档位在渲染层也过滤一次**：主进程按档位 / 开关过滤工具表，渲染层发送前再按同一张表过滤一次（老配置自动注入的那条「笔记知识库」不会因为档位变化被硬塞回已关闭的连接器）。
